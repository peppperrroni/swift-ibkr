# Decisions

| Decision | Why | Rejected |
|---|---|---|
| `orderType` and `tif` stay IB's strings; `action` is an enum (BUY / SELL / SSHORT) | IB's order types and TIFs are a long, growing list; actions are closed | enums for orderType/tif |
| Order status is an open set (`struct OrderStatus: RawRepresentable`), unknown statuses are kept | IB adds statuses; dropping one loses state | closed enum |
| Outgoing text outside 0x20...0x7E throws `IBEncodingError.nonASCII(field:)` | IB's own client refuses it (error 579); Russian preset names cannot go into orderRef as is | silently transliterating or sending UTF-8 |
| Execution and order times stay IB's raw strings in stage 1 | formats vary by account and message | parsing into `Date` |
| Fills join by execId in either order; a correction (execId minus its last segment, higher suffix) replaces the fill in place; a lower or resent superseded execId is dropped; unmatched halves are kept for the session | an execution and its commission arrive as separate messages, in either order, and IB resends and corrects them | evicting unmatched halves: a day's volume is small |
| A fill is published only when execDetails and commissionReport are both present; correction key = execId without its last `.`-segment | commission arrives separately; corrections reuse the execId prefix | publishing fills without commission |
| Trackers publish only real changes; an identical repeat publishes nothing | IB repeats messages | publishing every message |
| Error codes: notice — 2100...2199, 10167, 399, 404, 161, 10147, 10148, 165, 1101, 1102; warning — 105, 321, 329, 434, 492; order cancelled — 202; everything else fatal | an explicit table instead of a generic rule: 10167 would kill delayed data, 202 would mark every cancel a rejection | generic rule by code range |
| Connect-time sync sends reqAllOpenOrders, reqCompletedOrders, reqExecutions, reqPositions, then reqAccountUpdates for a single account or one reqAccountUpdatesMulti (model `""`, ledgerAndNLV off) per account for several, and waits for their end markers (accountDownloadEnd, accountUpdateMultiEnd) (as `ib_async`) | state is complete before `connect` returns | lazy sync |
| `cancelOrder`'s time parameter is `manualCancelOrderTime` (spec and ib_async), default `""` so old call sites compile | one name across the library and its sources | `manualOrderCancelTime` (the protocol table's spelling) |
| `exerciseOptions` is fire-and-forget and returns its reqId: IB answers success with nothing, so an error for that id reaches only `messages()`. It refuses secType `BAG` and sends no primaryExchange; `override` is a `Bool` defaulting to false | a combo cannot be exercised; out 21 has no primaryExchange field | reusing the shared contract block |
| Modify = re-sent placeOrder with the same orderId | that is how the protocol modifies | a separate modify message (none exists) |
| Tick-by-tick without a subscription counts as done when it fails with a typed "no permission" error (10189) | those entitlements are absent on most accounts | requiring live data to pass |
| The `marketDepth` stream ends with `.noMarketDataPermission(code: 2152, text:)` and sends its cancel when 2152's text carries «Unknown market data permissions» and the part before it names no `Depth:` exchange; a 2152 that grants `Depth:` keeps the book open, and so does a 2152 without that phrase (a reworded message must not cut a book); 2152 stays a notice in the global table. Evidence: `liveMarketData.json` (paper, no data subscription, 2026-11-11) holds one frame for the depth reqId, `Exchanges - Top: IBEOS; OVERNIGHT; Unknown market data permissions - Depth: NASDAQ; ...`, then nothing for 15 s | a typed end is recoverable (the caller sees why and can fall back), silence is not (indistinguishable from a quiet book). The evidence is thin: the one `Top:` grant covers only IBEOS and OVERNIGHT, venues closed in regular hours, so it cannot tell «no depth» from «no depth right now»; both a 2152 that grants `Depth:` on some exchanges (rule: stay open) and one that grants `Top:` only on regular venues (rule: end) are unseen live | silence (the hang the stage closes); ending on any 2152 (kills a partly permitted book) |
| `marketDepth` yields the whole `DepthBook` after every update; position-indexed per side (insert/update set, delete removes, gaps dropped), fed by both 12 and 13; error 317 empties it and the stream goes on | the TWS port's `OrderBookFeed` wants snapshots and the book logic belongs in one place; matches `ib_async` | a raw `DepthUpdate` stream as in the spec sketch (every consumer would rebuild the book); ending the stream on 317 |
| Protocol version pinned to 178 like `ib_async` | one field layout, no protobuf (starts at 201) | version branches, protobuf |
| placeOrder defaults follow `ib_async` (openClose "O", usePriceMgmtAlgo "0") | proven in practice; the 2026-11-10 paper run placed an order with them and the gateway did not reject it | IB's own client defaults |
| One shared unset set (empty, 2147483647, 9223372036854775807, 1.7976931348623157E308, -9223372036854775808) for every optional reader | IB uses all of them as "no value"; per-reader sets drifted | per-type sentinel lists |
| placeOrder encodes every group `ib_async` sends at 178 (the `BAG` legs, delta-neutral, scale, hedge, the delta-neutral contract, algo params, PEG BENCH / BEST / MID, conditions and the IBKRATS tail) and refuses no layout; marketData and historicalData send a `BAG`'s legs too, and every other request refuses secType `BAG` (`.unsupported("secType BAG")`) | with every group modelled no order can misalign the bytes, so a refusal would only block valid orders; the other requests have no leg fields here (reqMktData's are modelled), so a `BAG` there would go out without its legs | refusing the layouts not yet checked live; sending a `BAG` without its legs |
| `marketData`'s `genericTicks` is `[Int]`, sent comma-joined (`"100,101,104"`) | IB's generic tick types are numbers; the join is the wire's only form, so the caller cannot misformat it | a `String` the caller joins |
| A `marketData` stream that gets tickSnapshotEnd (57) ends there and sends no cancel | `ib_async` ends the request at the snapshot end; IB has already closed a snapshot, so a cancel would only draw an error | leaving the stream open until the consumer stops it |
| deltaNeutralValidation (56) and the reroutes (91, 92) decode to `IBMessage` cases that reach `messages()` only, not a request stream; a reroute does not touch the stream, whose ticks go on under the same reqId | none of them ends or fails a request; `ib_async` only logs/forwards them, and the consumer who cares watches `messages()` | yielding them as `Tick` cases (they are not ticks); resubscribing on a reroute (IB already serves the ticks) |
| Stage 8-9 API names: calls `marketData(_:genericTicks:snapshot:regulatorySnapshot:)`, `tickers(_:genericTicks:depthRows:smartDepth:)`, `tickers(for:regulatorySnapshot:)`, `realTimeBars(_:whatToShow:rth:)`, `depthExchanges()`, `smartComponents(_:)`, `historicalTicks(_:start:end:count:whatToShow:rth:ignoreSize:)`, `headTimeStamp(_:whatToShow:rth:)`, `histogramData(_:period:rth:)`, `historicalSchedule(_:days:end:rth:)`; types `OptionComputation`, `EFPData`, `NewsTick`, `Ticker`, `DepthMarketDataDescription`, `SmartComponent`, `HistogramData`, `HistoricalSchedule`, `HistoricalSession`; fields keep `ib_async`'s names (`impliedVol`, `optPrice`, `undPrice`), except `listingExch` -> `listingExchange` and `articleId` -> `articleID` | one vocabulary with `ib_async`, so its docs and examples still read, with the Swift acronym rule (`ID`) applied as in the earlier stages | Swift-only renames of the greek fields (`impliedVolatility`) |
| `marketData` and `historicalData` accept a `BAG` (so `tickers`, `tickers(for:)` and `historicalSchedule` do too); `realTimeBars`, depth, tick-by-tick, historical ticks, the head timestamp and the histogram keep refusing it | `ib_async` sends the legs only in reqMktData and reqHistoricalData; the other requests would go out without them | sending a `BAG` without its legs |
| OrderTracker takes the connection's client id at construction; an error matches only `.api(clientID: own, orderID: requestID)` | IB sends order errors only to the owning client, so another client's order with the same id must never be touched | guessing the client from the last `sent`, or taking a lone orderID candidate |
| Orders and requests share ONE id sequence seeded from `nextValidId` (as `ib_async` does) | IB reports both orderId and reqId errors in the same field; stage 2's `IBClient` must never number requests from a separate counter | separate counters: an error on request N would hit order N |
| A fatal error sets an order `.inactive` only while IB has not acknowledged it (status still `.apiPending`); otherwise it records `rejectReason` and leaves the status to IB's orderStatus/openOrder | IB keeps an acknowledged order working when a modification (re-sent placeOrder) is rejected with 110 or 201, or on a warning missing from the table | `.inactive` on every non-final order |
| An `openOrder` never revives a final status | a late or replayed openOrder must not undo Filled/Cancelled | taking the openOrder status as is |
| A fatal error after a final status keeps the status and records `rejectReason` | the final status came from IB; the error is a late reply | overwriting the status |
| A `completedOrder` joined to an existing order first applies the held Filled openOrder for its permID, if any, then updates only status, completedTime, `order.parentPermID`, and `filled` / `remaining` when its filledQuantity is larger | v178 completedOrder lacks parentID etc.; the existing snapshot's contract/order (e.g. bracket parentID) are fuller; parentPermId comes only in completedOrder, so an openOrder applied later keeps it; a known order filled while the client was away must not publish `.filled` with `filled` 0 | replacing contract and order; leaving `filled` to an orderStatus that may never come |
| `completedOrder` has no orderId/clientId at 178; it joins by permID. A new snapshot from it is built from the held Filled openOrder for its permID when there is one (its orderID, clientID, contract and order), else from the completedOrder; it takes `filled` from field 82 (filledQuantity) and `remaining = totalQuantity - filledQuantity`, never below 0 | a cancelled order can be part-filled, so status alone says nothing about the fill | Filled implies filled = total |
| A nil `ExecutionFilter.clientID` is sent as "0" (`ib_async` default) | the default `ib_async` uses; confirmed live on 2026-11-10: client 78's connect-time reqExecutions returned client 77's fill | omitting the field |
| `IBClient`'s streams (`states()`, `messages()`, and the update streams of `orders()` and `executions()`) are fresh on every call; `states()` yields the current state first, `orders()` / `executions()` hand a snapshot alongside | any number of consumers can listen, and a late one still learns where the connection stands | one shared stream |
| `messages()` carries every decoded incoming message, including those routed to the trackers | a superset loses nothing and needs no filter | only the messages no request claimed (the spec's wording) |
| One timeout covers the whole `connect` (TCP, handshake, readiness, and the order, fill, position and account sync), 10 s by default | the caller waits for one thing, "ready", and bounds it once | separate timeouts per phase |
| A manual `connect` after a disconnect starts a fresh `OrderTracker`; an automatic reconnect keeps it; the `ExecutionTracker` is created once and survives reconnects; subscribers stay subscribed; streams end only when their consumer stops; reconnect is opt-in (a `ReconnectPolicy` given to `connect`) | the order tracker takes the client id, which may differ between manual connects; a reconnect reuses the stored client id, and spec stage 6 has the orders snapshot survive the drop (a fresh tracker left `orders().snapshot` empty for the whole outage); fills are keyed by execId, so the sync's replay of a known fill is an identical repeat and publishes nothing; consumers should not have to resubscribe | a fresh `ExecutionTracker` per connect, which re-published every fill of the day on reconnect; reconnect by default; finishing streams on disconnect |
| After a disconnect `orders()` and `executions()` keep returning the last connection's state until the next `connect` | the last known state beats an empty one; `states()` says it is stale | clearing them on disconnect |
| A reconnect replays orders as whole snapshots (harmless, consumers take the latest); an order completed while disconnected comes back through completedOrder and joins its known snapshot by permID. After a manual `connect` it arrives keyed by permID with orderID 0 | the automatic reconnect keeps the `OrderTracker`, so the permID index still holds the order; a fresh tracker has nothing to join a v178 completedOrder to (it has no orderId) | a fresh tracker per reconnect attempt (empty snapshot during the outage); carrying the tracker across manual connects, whose client id may differ |
| During `connect`, a fatal error with reqId −1 (e.g. 326 "client id already in use") or with the reqId of the sync's reqExecutions or of one of its reqAccountUpdatesMulti fails `connect` with `.ib(code:text:)`; after `connect` it only goes to `messages()` | IB refuses a client this way and then closes; a rejected sync request would otherwise wait out the timeout; reporting the code beats a bare "connection closed" or "timeout" | failing on the close that follows; waiting for the timeout |
| Requests leave through one FIFO writer task that applies the throttle (45 per sliding second) | a cancel can never overtake its order, even when the throttle delays both | a per-call sleep under actor reentrancy, which does not keep call order |
| `Transport` is internal; consumers get `IBClient()` over TCP, tests inject a fake through an internal init | no transport API to support before anyone needs one | a public transport protocol |
| `TCPSocket.close()` only shuts the socket down; the reader thread closes the handle once `recv` returned and no send holds it | closing in `close()` races a reader still inside `recv`, which could then touch a reused handle | closing the handle in `close()` |
| A loopback connect asks for no SYN retransmissions; remote hosts keep the OS default | Windows retries a refused SYN for ~2 s, so a closed 127.0.0.1 port would hang the connect and "localhost" would wait on ::1 before IPv4 | the default retries everywhere |
| 1101 and 1102 (connectivity restored) are notices | IB sends them after a brief gateway-to-IB outage; as fatal they would abort a `connect` that happens to span one | leaving them fatal |
| `placeOrder` returns the id as soon as the frame is queued, not on IB's acknowledgement | the caller needs the id to cancel or correlate; the outcome (ack, rejection) arrives through `orders()` | waiting for IB's openOrder / orderStatus |
| `placeOrder`, `modifyOrder`, `cancelOrder` require the state `.connected` | before `nextValidId` the id counter is 0, and an order sent mid-handshake would take an id IB has not issued | allowing them once the socket is up |
| Public memberwise initialisers for the stage-1 value types were added in stage 5 (2026-11-12) | consumers must be able to build every model they receive, to fake data in their own tests; `OrderKey` became internal, no public API uses it | leaving them to the TWS adapter's fakes |
| Live tests refuse to place anything unless every managed account starts with `DU` | the tests place real orders on whatever gateway is on 127.0.0.1:4002; a live account must never be touched by a test | trusting the port number to mean paper |
| Recorded frames replace every managed account id with `DU0000001`, inside every field | the recordings are committed; account ids are personal data and fixtures only need a stable one | committing raw frames, redacting by hand |
| The live fill test trades marketable limits with `outsideRTH` (BUY +1% of `IBKR_LIVE_FILL_PRICE`; SELL priced 1% under the BUY's fill price, after a 2026-11-10 run whose reference-priced SELL sat above a falling market) | IB does not fill MKT orders outside regular hours, and without a market-data subscription the test cannot read a price itself (stage 4). On 2026-11-10 IB's price cap refused +2% in regular hours (error 202: "We cannot accept an order at a limit price at or more aggressive than 357.97385", we sent 358.53 for a reference of 351.5; the cap was about 1.8% over market) | MKT orders limited to 14:30-21:00 UTC |
| A completedOrder's `totalQuantity` stays as IB sends it; only the tracker's `remaining` is clamped at 0 | the gateway sends a filled order's completedOrder with totalQuantity 0 and the size in filledQuantity (API log, 2026-11-10), so `remaining` came out -1 after a restart; `ib_async` passes the order through raw too (and leaves filled / remaining at 0) | replacing totalQuantity with filledQuantity in the tracker: a guess at IB's meaning that a consumer cannot undo |
| Positions are always on: `connect` sends reqPositions with the sync and waits for positionEnd; cancelPositions is sent only by a clean `disconnect()`; `positions()` is a snapshot + `AsyncStream<[Position]>` of whole sets, like `orders()` | a trading app needs positions from the first moment; reqPositions has no reqId, so there is no per-request error to throw; one subscription per connection needs no reference counting (as `ib_async`) | a per-call `AsyncThrowingStream` with reference counting and cancelPositions |
| A position of 0 is removed from the set; at a reconnect the old set stays visible and the new sync's positions are collected aside, replacing it whole at positionEnd. The `PositionTracker` lives across connections | a position closed while disconnected disappears at positionEnd, and no subscriber sees a half-built or merged set | merging the replay into the old set (a closed position would never leave); clearing at connect (an empty set in between) |
| `accountSummary` and `pnlSingle` streams end, throwing, when the connection ends (its error, `.connectionClosed` for `disconnect()`), and are not resumed on reconnect; a fatal IB error with the stream's reqId ends it with `.ib(code:text:)`, or with `.noMarketDataPermission` for a permission refusal; only a stream the consumer stopped, or one IB refused for want of market-data permission, sends its cancel | a reqId belongs to one connection, and a consumer whose `for try await` just ends cannot tell a drop from a quiet account; IB already dropped the subscription when it reports a fatal error or the socket closes; the exception is a permission refusal, where IB keeps the subscription open (it re-sent 10197 for the quotes reqId after the stream had ended, live 2026-11-11), so each retry would leak a market-data line unless the cancel goes out (a failed send is ignored) | re-sending the request on reconnect behind the consumer's back; finishing quietly (looks like the end of data); sending a cancel for a stream the client ended itself |
| A request stream's `route` returns true when it finished the stream itself (`contractDetails` and `matchingSymbols` at IB's end marker or single answer; `historicalBars` without `keepUpToDate` after its one batch); the registry then drops the entry first and its `cancel` is `nil`, so no cancel goes out | 9 (contractDetails) and 81 (matchingSymbols) have no cancel message at all; history without `keepUpToDate` is finished by IB, and a late cancel (25) would draw an error (366, no such request). Dropping the entry before the termination hop is what makes that hop send nothing | sending a cancel after the end marker; a separate registry for one-shot requests beside the streams |
| `marketDepth` buffers only the newest book (`openStream` takes a buffering policy, default `.unbounded`) | every element is a whole `DepthBook`, so a slow consumer needs only the latest and an unbounded queue of stale books would only grow; ticks, bars, tick-by-tick and lookups stay `.unbounded` because each element counts | `.unbounded` for depth too (unbounded memory for a slow consumer); a bounded buffer of several books (a consumer would still read stale ones) |
| One-shot lookups throw `IBClientError.cancelled` when their stream ends without the end marker, which only the calling task's cancellation causes | returning the partial list would look like a complete answer, and `CancellationError` would be a second error type behind a `throws(IBClientError)` signature | returning what had arrived; rethrowing `CancellationError` |
| `AccountValue.value` stays IB's string | some tags are text (`AccountType`), and the consumer knows which tags it asked for | a `Decimal` value (fails on text tags) or a `Decimal?` beside the string (two fields for one value) |
| The package is public on GitHub under MIT | it contains no IB code (only field layouts are taken from ib_async, BSD-licensed; IB's ibapi is non-commercial and nothing of it is copied), so nothing stops an open licence | keeping it private; Apache-2.0 (the patent grant buys nothing here) |
| A fatal IB error for a stream's reqId ends it with `IBClientError.noMarketDataPermission(code:text:)` when `ErrorCode.isNoMarketDataPermission` holds (354, 10089, 10168, 10186, 10197; 162 only when its text contains `permission` or `different IP`, and 10189 (tick-by-tick's catch-all) and 420 (real-time bars) only when it contains `permission`, case-insensitive), else `.ib(code:text:)`; this holds for every stream kind | a UI must tell "not subscribed" from a real failure, and 162 is IB's catch-all for history (pacing, cancels), so the code alone would mislabel them | matching on the code alone (162 pacing becomes a permission error); the consumer parsing `.ib` text |
| Notices with a reqId are handed to that stream's `route`, which ignores what it does not know; 202 is not routed | a stream may want to react to a notice (the depth reset, 317) without ending; today none does | dropping notices before the registry |
| 317 (depth reset), 10090 and 10091 (part of the data not subscribed) are notices | data still flows after each, and the depth stream empties its book and goes on; 10225 (bust event) stays fatal, for `realTimeBars` too: the consumer subscribes again, as `ib_async`'s silent resubscribe is hidden traffic | leaving them fatal (ends a live stream for a harmless message); resubscribing for the consumer |
| `setMarketDataType` sends 59, requires a connection, and is not remembered across reconnects | the type is per connection on IB's side, and replaying it behind the consumer's back would be hidden traffic; README says to set it after `connect` | storing it and resending it in the sync |
| tickReqParams (81) decodes as `Tick.requestParameters` and `marketData` yields it; `IBMessage.tickRequestParameters` is removed | 81 carries its reqId and belongs to that market-data request, so the stream that asked for it should carry it; a `Tick` case keeps the stream's element type unchanged | keeping 81 as its own `IBMessage` case that no stream yields; a second stream element type for parameters |
| tickOptionComputation (21) turns IB's "not computed" into `nil`: `-1` for impliedVol, optPrice, pvDividend and undPrice, `-2` for delta, gamma, vega and theta | unset is `nil` everywhere in the API, and a `-2` vega read as a real number is a wrong greek; `ib_async` maps the same values except vega and theta, which it keeps at `-2` (an apparent slip in its wrapper) | `ib_async`'s mapping verbatim; keeping every sentinel |
| `TickField.live` maps the delayed greek fields 80-83 to 10-13 and the delayed yields 103/104 to 50/51 | delayed option computations arrive on 80-83 and a consumer keys greeks by the live field, as it does prices; `ib_async` folds the delayed yields into `bidYield`/`askYield` | leaving 80-83 and 103/104 unmapped |
| A news tick (84) keeps `timeStamp` as IB's raw `Int`; news reaches consumers only through `marketData` and stays out of `Ticker`, as in `ib_async` | `ib_async` documents no unit for it, so a `Date` would be a guess | a `Date` in milliseconds; a news field on `Ticker` |
| `Ticker` has named fields for bid, ask, last and their sizes, OHLC, volume, `lastTimestamp`, the five greeks (10-13 and 53), the request parameters and the depth book; `apply(_:)` keys every tick by its live field and puts every other tick into `prices`, `sizes`, `generics`, `strings` or `efp`. RT volume, fundamental ratios and dividends stay raw strings; there are no `prev…` fields; a bid or ask with size 0 has its price `nil`, and an empty last (-1, size 0) after a close is `nil`; RT volume (48, 77) does not move `last` or `lastSize`, unlike `ib_async`: `last` comes from tick 4 only | the named fields are what a quote screen reads, and the dictionaries keep every other tick without one property per IB field number; parsing RT volume, ratios and dividends would be new types for strings IB documents loosely, and parsing IB's loosely documented RT volume string into last/lastSize is a new type nobody asked for; `prev…` is history a consumer can keep itself; the size-0 and empty-last rules are `ib_async`'s, so a side IB has emptied does not show a stale price | `ib_async`'s ~80 named fields; parsed RT volume, ratios and dividends; `prev…` fields; keeping IB's -1 on an empty side |
| `tickers` composes `marketData` and, with `depthRows`, `marketDepth`, opened first; it yields the whole `Ticker` after every tick or book, with no deduplication, and buffers only the newest, like `marketDepth`. Ticks pass through an unbounded private channel before the fold. The first inner error ends it with that error; however it ends, a reader task per inner stream is cancelled, which stops that stream and sends its cancel; an open error stops what was already opened | a whole value per element lets a slow consumer skip to the newest without losing state, while a dropped tick before the fold would lose it; depth refuses everything `marketData` refuses and BAG too, so opening it first means a refused book has opened nothing; cancelling a reader is deterministic, freeing an unread stream has no promised time | deduplicating unchanged tickers; an unbounded outer stream; opening `marketData` first (a refused BAG book leaked a quote line); relying on deallocation to send cancels |
| `tickers(for:)` sends every snapshot request before reading any, folds each to its snapshot end in a task group and returns in the order of `contracts`; the first error is thrown and the group's cancellation stops every request still open, sending its cancel; a cancelled caller throws `.cancelled` | sending all first is `ib_async`'s `reqTickersAsync`, so the snapshots run in parallel; a typed failure tells the caller which request failed, where a partial ticker would look like a quiet market | `ib_async`'s partial tickers on error; one request at a time |
| `Bar.time` is a `Date`: epoch seconds, or 00:00 UTC for an 8-character `YYYYMMDD` bar; `historicalBars` always sends `formatDate` 2 (SCHEDULE alone sends 1, see `historicalSchedule`) | one type for every bar size, and no timezone guess: formatDate 1 intraday text carries no zone (only the login zone, unknown to the client), while epoch seconds are exact; daily bars come as dates under either formatDate, and UTC midnight of that day is the least surprising instant | formatDate 1 with a configured zone; a `Bar.date` string or a day/instant enum; local midnight |
| `historicalSchedule(_:days:end:rth:)` is a one-shot over reqHistoricalData with `whatToShow` SCHEDULE (formatDate 1, bar size "1 day", duration "N D"); its sessions stay IB's text; `historicalBars` refuses SCHEDULE with `.encoding(.unsupported("whatToShow SCHEDULE"))` before sending | IB answers SCHEDULE with 106, not 17, so a bar stream would wait forever; schedule times carry the schedule's zone, which a `Date` would lose; the stream keeps the cancel so a permission refusal (IB leaves it open) is closed | decoding SCHEDULE as bars; parsing the times into `Date`; sending no cancel |
| `historicalTicks(_:start:end:count:whatToShow:rth:ignoreSize:)` returns `[TickByTick]` (all three of 96, 97, 98 decode to the same enum) and is a one-shot that sends no cancel; the bid/ask mask and the midpoint size are dropped, as in tick-by-tick; `whatToShow` is IB's string; `start`/`end` go out as the library's `yyyyMMdd-HH:mm:ss` UTC text, `nil` as `""` | the answer is one batch with a `done` flag and IB has no cancel for it, so a stream or a cancel would be dead weight; the date text is the one `historicalBars` already sends, where `ib_async` writes `yyyyMMdd HH:mm:ss UTC` | a separate type for historical ticks; a stream; keeping the masks |
| `headTimeStamp(_:whatToShow:rth:)` asks with formatDate 2 and returns a `Date` (an 8-character day is 00:00 UTC); it sends cancel 90 after the answer, as `ib_async` does | IB keeps the head-timestamp request open after answering; `ib_async` cancels it | leaving it open (a leaked server-side request per call) |
| `histogramData(_:period:rth:)` is a one-shot that sends 89 only for a caller cancelled before the answer; `HistogramData.count` is an `Int` | IB closes a histogram request with its answer; `ib_async` types the count as an int | always sending 89; a `Decimal` count |
| `realTimeBars` is a request stream like `tickByTick`: it sends 50 with barSize 5 (IB offers no other) and an empty options field, yields each bar as `Bar` (message `.realTimeBar`), never ends itself, and keeps IB's -1 volume, average and count on MIDPOINT/BID/ASK as `Bar` does for history | the 5-second size is fixed by IB, so it is not a parameter; one `Bar` type keeps history and live bars interchangeable | a `barSize` parameter IB would refuse; mapping -1 to nil for live bars only |
| CI on every push and pull request, one job per OS: macOS runs `swift test` and builds for iOS (`xcodebuild -scheme swift-ibkr -destination 'generic/platform=iOS'`); Linux runs `swift test` in the official `swift:6.0` and `swift:latest` images; Windows runs it on 6.4.2 installed by `compnerd/gha-setup-swift`, pinned by SHA. `IBKR_LIVE` is never set, so the live tests skip | the socket has a branch per OS and only the Windows one had ever been built; 6.0 is the tools floor and `latest` catches what newer compilers reject (the first run caught a test helper that needed 6.4); iOS is built, not tested: no code path is iOS-only, and the Darwin socket branch is the one macOS tests | a Swift-version matrix on every OS; iOS tests in a simulator; testing only on the owner's machines |
| The CocoaPods pod is `SwiftIBKR`, the module stays `IBKR` (`s.module_name`), version 0.5.0; CI runs `pod lib lint SwiftIBKR.podspec` (local source, so no tag is needed). ## Error-code table

| Kind | Codes | Effect |
|---|---|---|
| notice | 2100...2199, 10167, 399, 404, 161, 10147, 10148, 165, 1101, 1102, 317, 10090, 10091 | informational, never fails a request |
| warning | 105, 321, 329, 434, 492 | `ib_async`'s warning codes: ends the request stream or sync request it names, like a fatal; records `rejectReason` on an order but never sets it `.inactive` |
| order cancelled | 202 | the cancel confirmation, not a rejection; non-blank text after `reason:` (IB's price cap) becomes the order's `rejectReason` |
| fatal | everything else | fails the request it belongs to |

A message id that is not a number decodes as malformed with id 0: there is no id to report.
