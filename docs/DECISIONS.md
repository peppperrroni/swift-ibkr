# Decisions

| Decision | Why | Rejected |
|---|---|---|
| `orderType` and `tif` stay IB's strings; `action` is an enum (BUY / SELL / SSHORT) | IB's order types and TIFs are a long, growing list; actions are closed | enums for orderType/tif |
| Order status is an open set (`struct OrderStatus: RawRepresentable`), unknown statuses are kept | IB adds statuses; dropping one loses state | closed enum |
| Outgoing text outside 0x20...0x7E throws `IBEncodingError.nonASCII(field:)` | IB's own client refuses it (error 579); Russian preset names cannot go into orderRef as is | silently transliterating or sending UTF-8 |
| Execution and order times stay IB's raw strings in stage 1 | formats vary by account and message | parsing into `Date` |
| Fills join by execId in either order; a correction (execId minus its last segment, higher suffix) replaces the fill in place; a lower or resent superseded execId is dropped; unmatched halves are kept for the session | an execution and its commission arrive as separate messages, in either order, and IB resends and corrects them | evicting unmatched halves: a day's volume is small |
| A fill is published only when execDetails and commissionReport are both present; correction key = execId without its last `.`-segment | commission arrives separately; corrections reuse the execId prefix | publishing fills without commission |
| Trackers publish only real changes; an identical repeat publishes nothing | IB repeats messages | publishing every message |
| Error codes: notice — 2100...2199, 10167, 399, 404, 161, 10147, 10148, 165, 1101, 1102; warning — 105, 321, 329, 434, 492; order cancelled — 202; everything else fatal | an explicit table instead of a generic rule: 10167 would kill delayed data, 202 would mark every cancel a rejection | generic rule by code range |
| Connect-time sync sends reqAllOpenOrders, reqCompletedOrders, reqExecutions and waits for their end markers (as `ib_async`) | state is complete before `connect` returns | lazy sync |
| Modify = re-sent placeOrder with the same orderId | that is how the protocol modifies | a separate modify message (none exists) |
| Tick-by-tick without a subscription counts as done when it fails with a typed "no permission" error (10189); depth gets notice 2152 and then silence, accepted for stage 4 (KNOWN-GAPS) | those entitlements are absent on most accounts; 2152's exchange list is fragile to parse and permissions can be partial, so stage 5 decides with real depth data | requiring live data to pass; ending the depth stream on 2152 |
| `marketDepth` yields the whole `DepthBook` after every update; position-indexed per side (insert/update set, delete removes, gaps dropped), fed by both 12 and 13; error 317 empties it and the stream goes on | the TWS port's `OrderBookFeed` wants snapshots and the book logic belongs in one place; matches `ib_async` | a raw `DepthUpdate` stream as in the spec sketch (every consumer would rebuild the book); ending the stream on 317 |
| Protocol version pinned to 178 like `ib_async` | one field layout, no protobuf (starts at 201) | version branches, protobuf |
| placeOrder defaults follow `ib_async` (openClose "O", usePriceMgmtAlgo "0") | proven in practice; the 2026-11-10 paper run placed an order with them and the gateway did not reject it | IB's own client defaults |
| One shared unset set (empty, 2147483647, 9223372036854775807, 1.7976931348623157E308, -9223372036854775808) for every optional reader | IB uses all of them as "no value"; per-reader sets drifted | per-type sentinel lists |
| placeOrder encodes only the base layout; secType BAG, PEG order types and exchange IBKRATS throw `.unsupported` | the table adds combo-leg / PEG / IBKRATS fields the encoder does not emit, which would misalign the bytes | emitting the base layout silently |
| OrderTracker takes the connection's client id at construction; an error matches only `.api(clientID: own, orderID: requestID)` | IB sends order errors only to the owning client, so another client's order with the same id must never be touched | guessing the client from the last `sent`, or taking a lone orderID candidate |
| Orders and requests share ONE id sequence seeded from `nextValidId` (as `ib_async` does) | IB reports both orderId and reqId errors in the same field; stage 2's `IBClient` must never number requests from a separate counter | separate counters: an error on request N would hit order N |
| A fatal error sets an order `.inactive` only while IB has not acknowledged it (status still `.apiPending`); otherwise it records `rejectReason` and leaves the status to IB's orderStatus/openOrder | IB keeps an acknowledged order working when a modification (re-sent placeOrder) is rejected with 110 or 201, or on a warning missing from the table | `.inactive` on every non-final order |
| An `openOrder` never revives a final status | a late or replayed openOrder must not undo Filled/Cancelled | taking the openOrder status as is |
| A fatal error after a final status keeps the status and records `rejectReason` | the final status came from IB; the error is a late reply | overwriting the status |
| A `completedOrder` joined to an existing order updates only status and completedTime | v178 completedOrder lacks parentID etc.; the existing snapshot's contract/order (e.g. bracket parentID) are fuller | replacing contract and order |
| `completedOrder` has no orderId/clientId at 178; it joins by permID. A new snapshot from it takes `filled` from field 82 (filledQuantity) and `remaining = totalQuantity - filledQuantity` | a cancelled order can be part-filled, so status alone says nothing about the fill | Filled implies filled = total |
| A nil `ExecutionFilter.clientID` is sent as "0" (`ib_async` default) | the default `ib_async` uses; confirmed live on 2026-11-10: client 78's connect-time reqExecutions returned client 77's fill | omitting the field |
| `IBClient`'s streams (`states()`, `messages()`, and the update streams of `orders()` and `executions()`) are fresh on every call; `states()` yields the current state first, `orders()` / `executions()` hand a snapshot alongside | any number of consumers can listen, and a late one still learns where the connection stands | one shared stream |
| `messages()` carries every decoded incoming message, including those routed to the trackers | a superset loses nothing and needs no filter | only the messages no request claimed (the spec's wording) |
| One timeout covers the whole `connect` (TCP, handshake, readiness, order / fill sync), 10 s by default | the caller waits for one thing, "ready", and bounds it once | separate timeouts per phase |
| `connect` after a disconnect starts a fresh `OrderTracker`; the `ExecutionTracker` is created once and survives reconnects; subscribers stay subscribed; streams end only when their consumer stops; nothing reconnects automatically | the order tracker takes the client id, which may differ between connects; fills are keyed by execId, so the sync's replay of a known fill is an identical repeat and publishes nothing; consumers should not have to resubscribe | a fresh `ExecutionTracker` per connect, which re-published every fill of the day on reconnect; auto-reconnect; finishing streams on disconnect |
| After a disconnect `orders()` and `executions()` keep returning the last connection's state until the next `connect` | the last known state beats an empty one; `states()` says it is stale | clearing them on disconnect |
| A reconnect replays orders as whole snapshots (harmless, consumers take the latest); an order completed while disconnected comes back through completedOrder, keyed by permID with orderID 0 | the fresh `OrderTracker` has nothing to join a v178 completedOrder to (it has no orderId) | carrying the order tracker across connects, whose client id may differ |
| During `connect`, a fatal error with reqId −1 (e.g. 326 "client id already in use") or with the sync's reqExecutions id fails `connect` with `.ib(code:text:)`; after `connect` it only goes to `messages()` | IB refuses a client this way and then closes; a rejected sync request would otherwise wait out the timeout; reporting the code beats a bare "connection closed" or "timeout" | failing on the close that follows; waiting for the timeout |
| Requests leave through one FIFO writer task that applies the throttle (45 per sliding second) | a cancel can never overtake its order, even when the throttle delays both | a per-call sleep under actor reentrancy, which does not keep call order |
| `Transport` is internal; consumers get `IBClient()` over TCP, tests inject a fake through an internal init | no transport API to support before anyone needs one | a public transport protocol |
| `TCPSocket.close()` only shuts the socket down; the reader thread closes the handle once `recv` returned and no send holds it | closing in `close()` races a reader still inside `recv`, which could then touch a reused handle | closing the handle in `close()` |
| A loopback connect asks for no SYN retransmissions; remote hosts keep the OS default | Windows retries a refused SYN for ~2 s, so a closed 127.0.0.1 port would hang the connect and "localhost" would wait on ::1 before IPv4 | the default retries everywhere |
| 1101 and 1102 (connectivity restored) are notices | IB sends them after a brief gateway-to-IB outage; as fatal they would abort a `connect` that happens to span one | leaving them fatal |
| `placeOrder` returns the id as soon as the frame is queued, not on IB's acknowledgement | the caller needs the id to cancel or correlate; the outcome (ack, rejection) arrives through `orders()` | waiting for IB's openOrder / orderStatus |
| `placeOrder`, `modifyOrder`, `cancelOrder` require the state `.connected` | before `nextValidId` the id counter is 0, and an order sent mid-handshake would take an id IB has not issued | allowing them once the socket is up |
| Public memberwise initialisers for the stage-1 value types were added in stage 5 (2026-11-12) | consumers must be able to build every model they receive, to fake data in their own tests; `OrderKey` became internal, no public API uses it | leaving them to the TWS adapter's fakes |
| Live tests refuse to place anything unless every managed account starts with `DU` | the tests place real orders on whatever gateway is on 127.0.0.1:4002; a live account must never be touched by a test | trusting the port number to mean paper |
| Recorded frames replace every managed account id with `DU0000001`, inside every field | the recordings are committed; account ids are personal data and fixtures only need a stable one | committing raw frames, redacting by hand |
| The live fill test trades marketable limits with `outsideRTH` (BUY +1% of `IBKR_LIVE_FILL_PRICE`; SELL priced 1% under the BUY's fill price, after a 2026-11-10 run whose reference-priced SELL sat above a falling market) | IB does not fill MKT orders outside regular hours, and without a market-data subscription the test cannot read a price itself (stage 4). On 2026-11-10 IB's price cap refused +2% in regular hours (error 202: "We cannot accept an order at a limit price at or more aggressive than 357.97385", we sent 358.53 for a reference of 351.5; the cap was about 1.8% over market) | MKT orders limited to 14:30-21:00 UTC |
| A completedOrder's `totalQuantity` stays as IB sends it; only the tracker's `remaining` is clamped at 0 | the gateway sends a filled order's completedOrder with totalQuantity 0 and the size in filledQuantity (API log, 2026-11-10), so `remaining` came out -1 after a restart; `ib_async` passes the order through raw too (and leaves filled / remaining at 0) | replacing totalQuantity with filledQuantity in the tracker: a guess at IB's meaning that a consumer cannot undo |
| Positions are always on: `connect` sends reqPositions with the sync and waits for positionEnd; cancelPositions is never sent; `positions()` is a snapshot + `AsyncStream<[Position]>` of whole sets, like `orders()` | a trading app needs positions from the first moment; reqPositions has no reqId, so there is no per-request error to throw; one subscription per connection needs no reference counting (as `ib_async`) | a per-call `AsyncThrowingStream` with reference counting and cancelPositions |
| A position of 0 is removed from the set; at a reconnect the old set stays visible and the new sync's positions are collected aside, replacing it whole at positionEnd. The `PositionTracker` lives across connections | a position closed while disconnected disappears at positionEnd, and no subscriber sees a half-built or merged set | merging the replay into the old set (a closed position would never leave); clearing at connect (an empty set in between) |
| `accountSummary` and `pnlSingle` streams end, throwing, when the connection ends (its error, `.connectionClosed` for `disconnect()`), and are not resumed on reconnect; a fatal IB error with the stream's reqId ends it with `.ib(code:text:)`, or with `.noMarketDataPermission` for a permission refusal; only a stream the consumer stopped, or one IB refused for want of market-data permission, sends its cancel | a reqId belongs to one connection, and a consumer whose `for try await` just ends cannot tell a drop from a quiet account; IB already dropped the subscription when it reports a fatal error or the socket closes; the exception is a permission refusal, where IB keeps the subscription open (it re-sent 10197 for the quotes reqId after the stream had ended, live 2026-11-11), so each retry would leak a market-data line unless the cancel goes out (a failed send is ignored) | re-sending the request on reconnect behind the consumer's back; finishing quietly (looks like the end of data); sending a cancel for a stream the client ended itself |
| A request stream's `route` returns true when it finished the stream itself (`contractDetails` and `matchingSymbols` at IB's end marker or single answer; `historicalBars` without `keepUpToDate` after its one batch); the registry then drops the entry first and its `cancel` is `nil`, so no cancel goes out | 9 (contractDetails) and 81 (matchingSymbols) have no cancel message at all; history without `keepUpToDate` is finished by IB, and a late cancel (25) would draw an error (366, no such request). Dropping the entry before the termination hop is what makes that hop send nothing | sending a cancel after the end marker; a separate registry for one-shot requests beside the streams |
| `marketDepth` buffers only the newest book (`openStream` takes a buffering policy, default `.unbounded`) | every element is a whole `DepthBook`, so a slow consumer needs only the latest and an unbounded queue of stale books would only grow; ticks, bars, tick-by-tick and lookups stay `.unbounded` because each element counts | `.unbounded` for depth too (unbounded memory for a slow consumer); a bounded buffer of several books (a consumer would still read stale ones) |
| One-shot lookups throw `IBClientError.cancelled` when their stream ends without the end marker, which only the calling task's cancellation causes | returning the partial list would look like a complete answer, and `CancellationError` would be a second error type behind a `throws(IBClientError)` signature | returning what had arrived; rethrowing `CancellationError` |
| `AccountValue.value` stays IB's string | some tags are text (`AccountType`), and the consumer knows which tags it asked for | a `Decimal` value (fails on text tags) or a `Decimal?` beside the string (two fields for one value) |
| The package is public on GitHub under MIT | it contains no IB code (only field layouts are taken from ib_async, BSD-licensed; IB's ibapi is non-commercial and nothing of it is copied), so nothing stops an open licence | keeping it private; Apache-2.0 (the patent grant buys nothing here) |
| A fatal IB error for a stream's reqId ends it with `IBClientError.noMarketDataPermission(code:text:)` when `ErrorCode.isNoMarketDataPermission` holds (354, 10089, 10168, 10186, 10197; 162 only when its text contains `permission` or `different IP`, and 10189 (tick-by-tick's catch-all) only when it contains `permission`, case-insensitive), else `.ib(code:text:)`; this holds for every stream kind | a UI must tell "not subscribed" from a real failure, and 162 is IB's catch-all for history (pacing, cancels), so the code alone would mislabel them | matching on the code alone (162 pacing becomes a permission error); the consumer parsing `.ib` text |
| Notices with a reqId are handed to that stream's `route`, which ignores what it does not know; 202 is not routed | a stream may want to react to a notice (the depth reset, 317) without ending; today none does | dropping notices before the registry |
| 317 (depth reset), 10090 and 10091 (part of the data not subscribed) are notices | data still flows after each, and the depth stream empties its book and goes on; 10225 (bust event) stays fatal: the consumer subscribes again, as `ib_async`'s silent resubscribe is hidden traffic | leaving them fatal (ends a live stream for a harmless message); resubscribing for the consumer |
| `setMarketDataType` sends 59, requires a connection, and is not remembered across reconnects | the type is per connection on IB's side, and replaying it behind the consumer's back would be hidden traffic; README says to set it after `connect` | storing it and resending it in the sync |
| `marketData` yields only `.tick` for its reqId; `.tickRequestParameters` (81) is not yielded | the stream's element is `Tick`; 81 carries the minTick and exchange, which a trading UI reads from contract details | a second element case for parameters |
| `Bar.time` is a `Date`: epoch seconds, or 00:00 UTC for an 8-character `YYYYMMDD` bar; `historicalBars` always sends `formatDate` 2 | one type for every bar size, and no timezone guess: formatDate 1 intraday text carries no zone (only the login zone, unknown to the client), while epoch seconds are exact; daily bars come as dates under either formatDate, and UTC midnight of that day is the least surprising instant | formatDate 1 with a configured zone; a `Bar.date` string or a day/instant enum; local midnight |
| CI on every push and pull request, one job per OS: macOS runs `swift test` and builds for iOS (`xcodebuild -scheme swift-ibkr -destination 'generic/platform=iOS'`); Linux runs `swift test` in the official `swift:6.0` and `swift:latest` images; Windows runs it on 6.4.2 installed by `compnerd/gha-setup-swift`, pinned by SHA. `IBKR_LIVE` is never set, so the live tests skip | the socket has a branch per OS and only the Windows one had ever been built; 6.0 is the tools floor and `latest` catches what newer compilers reject (the first run caught a test helper that needed 6.4); iOS is built, not tested: no code path is iOS-only, and the Darwin socket branch is the one macOS tests | a Swift-version matrix on every OS; iOS tests in a simulator; testing only on the owner's machines |
| The CocoaPods pod is `SwiftIBKR`, the module stays `IBKR` (`s.module_name`), version 0.5.0; CI runs `pod lib lint SwiftIBKR.podspec` (local source, so no tag is needed). Docs build without a docc plugin dependency | a pod named `IBKR` reads as Interactive Brokers' own; keeping the module name means `import IBKR` is identical under SPM and CocoaPods; adding `swift-docc-plugin` would give a dependency-free package its first dependency | pod named `IBKR`; module `SwiftIBKR`; `pod spec lint` (needs the tag); the docc plugin dependency |
| A peer reset or abort (WSAECONNRESET / WSAECONNABORTED, EPIPE / ECONNRESET) is `.connectionClosed` on both read and write | To a consumer a reset peer is a closed connection; the read path's `.transport("recv: ...")` raced the write path on Windows (2 runs in 10) | keeping `.transport` for a reset |
| `ErrorKind.warning` (105, 321, 329, 434, 492, `ib_async`'s warning set) ends a request stream or a sync request like a fatal, but on an order only records `rejectReason`: a new order with no orderStatus stays `.apiPending`. 110 stays fatal | deviation from the spec's "not fatal": our streams have no timeout, so a stream left open on a refused request would hang; the order side matches `ib_async`, which logs a warning and leaves the order alone; costs: consumers see streams end on warnings, and in rare cases an order stays pending with no status | warnings as notices (hung streams); treating 110 as a warning |
| Error `text` is `\uXXXX`-decoded (surrogate pairs joined; short, non-hex and lone-surrogate escapes stay literal); `advancedOrderRejectJson` is kept raw | IB's own client unescapes text from server 153; the JSON is already valid JSON where `\u0022` means a quote, and decoding it would break it | decoding both |

## Error-code table

| Kind | Codes | Effect |
|---|---|---|
| notice | 2100...2199, 10167, 399, 404, 161, 10147, 10148, 165, 1101, 1102, 317, 10090, 10091 | informational, never fails a request |
| warning | 105, 321, 329, 434, 492 | `ib_async`'s warning codes: ends the request stream or sync request it names, like a fatal; records `rejectReason` on an order but never sets it `.inactive` |
| order cancelled | 202 | the cancel confirmation, not a rejection |
| fatal | everything else | fails the request it belongs to |

A message id that is not a number decodes as malformed with id 0: there is no id to report.
| Id-less one-shots (`currentTime`, `managedAccounts`, `nextOrderID`) wait as request streams under local keys -2, -3, ...; `routeToStream` offers `currentTime`, `managedAccounts` and `nextValidID` to them oldest first, and only the first waiter that takes a message gets it | these replies carry no reqId, so two concurrent calls must each take one answer and never share one; the keys stay below -1, which IB uses for "no request" in errors | one shared continuation (a second call would clobber the first); matching by arrival order alone |
| `nextOrderID()` returns `max(local next id, IB's answer)` and consumes nothing | the order-id rule from connect holds: an answer below the local id never lowers it, since placeOrder and request ids share one sequence | returning IB's answer as is |
| `userInfo` fails on any error that fails a request (fatal or warning) for its reqId | same rule as every other request stream | fatal only |
| `reqAutoOpenOrders` (out 15) and `reqGlobalCancel` (out 58) are sent only by `setAutoOpenOrders` and `cancelAllOrders`, and are not sent at connect | binding other clients' orders is an opt-in, and the connect-time sync already asks for all open orders; stage 7 must not add these two requests again | binding at connect (as TWS API clients with clientId 0 often do) |
| Session API names: `currentTime()`, `managedAccounts()`, `nextOrderID()`, `userInfo()`, `setServerLogLevel(_:)`, `setAutoOpenOrders(_:)`, `cancelAllOrders()`; `ServerLogLevel` is an Int enum 1...5 | the settings throw synchronously and send; the one-shots wait like `contractDetails` | `reqCurrentTime`-style names mirroring IB's |
