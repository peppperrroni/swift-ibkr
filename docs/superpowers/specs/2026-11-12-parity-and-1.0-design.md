# swift-ibkr: охват ib_async и выпуск 1.0

Дата: 2026-11-12. Продолжает [`2026-11-09-swift-ibkr-design.md`](2026-11-09-swift-ibkr-design.md): этапы 1–4 сделаны
и лежат на `main`. Владелец решил:
- swift-ibkr становится полноценной публичной Swift-библиотекой для всех, кто пишет под IB;
- по охвату она должна сравняться с ib_async;
- выходит она тегом 1.0 со всем, что положено типичному фреймворку, включая установку через SPM и CocoaPods;
- подключение к TWS (бывший этап 5) идёт после 1.0;
- работать до готового релиза без вопросов к владельцу.

Решения, принятые мной без владельца, помечены **(моё)**.

## Зачем

Готового Swift-SDK для IB нет. ib_async (Python, BSD, наследник ib_insync) — фактический стандарт по охвату и по
тому, как держать состояние. Успех такой: человек, который знает ib_async, ставит swift-ibkr через SPM или
CocoaPods и находит каждую возможность ib_async, связанную с сокетом, в Swift-виде. Дальше он читает DocC-документацию
и собирает пример. CI собирает и тестирует пакет на macOS, Linux и Windows и собирает его под iOS.

## Опорная точка

ib_async 2.1.0, коммит `ab629f34c1823ea4c1542f32f07377208a86bdfd` (2025-12-06).
- Версии клиента 157–178, только текстовый протокол без protobuf.
- Ни одно поле не зависит от версии выше 178, так что наша версия 178 покрывает всё.
- 80 исходящих мест отправки (id 1–25, 49–104) и 82 входящих обработчика (id 1–21, 45–47, 49–59, 61–107).
- Полный перечень с группировкой: «Перечень» ниже. Порядок полей каждого сообщения, как и раньше, берём из
  исходников ib_async и записываем в `docs/protocol-178.md`. Кода не копируем.

## Цели

1. **Протокол.** Каждое сообщение, которое ib_async отправляет или разбирает, есть в `IBRequest` / `IBMessage`
   с тестом кодека.
2. **Swift-API.** Каждая возможность ib_async, связанная с сокетом, доступна из `IBClient` в одном из трёх уже
   принятых видов:
   - **разовый запрос:** `async throws`, собирает ответ до `…End`;
   - **поток запроса:** `AsyncThrowingStream`, выход из `for await` шлёт отмену;
   - **снимок и поток:** всегда включённое состояние, синхронизированное при подключении.
3. **Состояние, как в ib_async:**
   - портфель и значения счёта;
   - `Ticker`, собирающий тики в цельную котировку;
   - what-if ордер;
   - `qualifyContracts`;
   - пакетные снимки котировок (`reqTickers`);
   - разовый сканер;
   - помощники для брекета и OCA;
   - фабрики контрактов (`Stock`, `Option`, `Future`…).
4. **Переподключение** (часть `Watchdog` без IBC). Сам отвечает за обрыв: переподключается с паузами между
   попытками и проверяет связь через `reqCurrentTime`. Подписчики снимков и потоков переживают обрыв, как сейчас.
5. **Flex-отчёты** (HTTPS Flex Web Service, как `FlexReport` в ib_async) — отдельным продуктом `IBKRFlex` в том
   же пакете, чтобы `IBKR` не тянул сетевой стек URLSession **(моё)**.
6. **Платформы:** macOS 13+, iOS 16+, Linux (Ubuntu, Swift 6.x), Windows (Swift 6.x).
7. **Фреймворк:**
   - публичные `init` у всех моделей, `Sendable` и doc-комментарии на всём публичном API;
   - DocC-каталог со статьями (начало работы, ордера, рыночные данные, переход с ib_async), опубликованный на
     GitHub Pages; `.spi.yml` для Swift Package Index;
   - CI на GitHub Actions: macOS (тесты, сборка под iOS, `pod lib lint`, документация), Linux и Windows (тесты);
   - `Examples/` с консольным примером;
   - `CHANGELOG.md`, `CONTRIBUTING.md`, шаблоны issue, podspec;
   - семантические версии; релиз `1.0.0` тегом и GitHub Release.
8. Без внешних зависимостей, как и раньше. Документацию собирает CI через `xcodebuild docbuild` и `docc`, плагин
   swift-docc в `Package.swift` не нужен **(моё)**.

## Не цели

- **protobuf и протокол 201+.** В ib_async их тоже нет.
- **Запуск и перезапуск самого Gateway или TWS** (IBC в `Watchdog`). Это управление процессом на Java, а не
  протокол.
- **Синхронный API, pandas, графики, интеграция с Qt и Jupyter.**
- **Android и musl.**
- **`setServerLogLevel` с разбором логов.** Сам запрос будет, логи — нет.

## Анти-цели

Действуют прежние анти-цели:
- нет кода `ibapi`;
- события не теряются;
- никаких `Double` для денег;
- никаких UNSET-чисел в публичных типах;
- ни одна ошибка разбора не проглатывается молча;
- подписки не утекают.

И новые:
- Ломать существующий API без нужды. Разрешено, пока версия не 1.0, но каждое изменение записывается в CHANGELOG.
- Публиковать возможность, у которой нет ни одного теста кодека.
- Хранить XML или JSON IB в собственных разобранных моделях там, где ib_async отдаёт строку: отчёты
  фундаментальных данных, параметры сканера, FA, WSH. У нас это тоже `String`. Разбор XML в `IBKR` не входит
  **(моё)**. Исключение — `IBKRFlex`, где разбор и есть суть.

## Этапы

Каждый этап получает свой план (`docs/superpowers/plans/`) и проходит SDD: на каждую задачу отдельный исполнитель
и отдельное ревью, в конце общее ревью ветки. Ветка этапа перематывается на `main` и пушится, когда тесты зелёные
и CI зелёный (владелец разрешил работать до релиза без вопросов). Документы (README, DECISIONS, KNOWN-GAPS,
protocol-178, CHANGELOG) меняются в том же коммите, что и поведение.

5. **Основа фреймворка.**
   - Платформы в `Package.swift`: `.macOS(.v13)`, `.iOS(.v16)`.
   - Сборка и тесты на macOS и Linux с починкой того, что сломается (Darwin- и Glibc-ветки сокета никогда не
     собирались).
   - CI на трёх ОС плюс сборка под iOS.
   - Публичные `init` у всех публичных моделей; неиспользуемый публичный `OrderKey` удалить.
   - `CHANGELOG.md` с разделом «Unreleased».

   Первым этапом, потому что все следующие этапы проверяет CI.

## Проверка

- **Кодек.** Каждое новое сообщение проверяется тестом на кадре, собранном по порядку полей ib_async, в обе
  стороны там, где это применимо.
- **Клиент.** Новые запросы проверяются на `FakeGateway`: отправленные поля, маршрутизация по reqId, отмена при
  выходе из потока, ошибка IB для запроса.
- **Живая проверка.** Один прогон в конце этапа 13 на paper-счёте, если Gateway запущен на 127.0.0.1:4002. Защита
  остаётся прежней: только счета `DU`, а реальный номер счёта в записях заменяется на `DU0000001`. Чего нет без
  подписки или без живого Gateway, остаётся пунктом KNOWN-GAPS, а не считается проверенным **(моё)**.
- **CI.** Ветку этапа перематываю на `main` только при зелёном CI на всех ОС.

## Решения после проверки строителем (все мои)

Владелец просил не задавать вопросов до релиза, поэтому вопросы строителя я решил сам.

1. **Переподключение.**
   - Включается по желанию и по умолчанию выключено: `connect(…, reconnect: ReconnectPolicy?)`, по умолчанию
     `nil`.
   - Ручной `disconnect()` его останавливает.
   - Снимки и потоки (`orders`, `executions`, `positions`, `portfolio`, `states`) переживают обрыв.
   - Потоки запросов по-прежнему заканчиваются ошибкой соединения, как и `Watchdog` в ib_async: потребитель
     запрашивает их заново. Так остаётся в силе строка DECISIONS о том, что запросы за спиной потребителя не
     повторяются.
   - `setMarketDataType` после переподключения не повторяется сам. Его повторяет потребитель, и документация
     об этом говорит.
   - Строка DECISIONS «без автопереподключения» меняется на «переподключение — по желанию».
2. **Открытые пункты KNOWN-GAPS, которые влияют на публичный API, закрываются до 1.0, а не уходят в 2.0.**
   - **Этап 6:**
     - `connect` прерывается при отмене задачи;
     - экранированный текст ошибок `\uXXXX` раскодируется;
     - таблица кодов-предупреждений сверяется с ib_async, и коды, которые ib_async считает предупреждениями,
       перестают быть фатальными.
   - **Этап 7:**
     - причина 202 сохраняется в снимке ордера;
     - снимок `.filled` с `filled` 0 из одного openOrder не публикуется, пока не придёт orderStatus;
     - у завершённых ордеров появляется `parentPermId`.
   - **Этап 8:** решение по молчанию стакана после 2152, принятое по записанным живым кадрам.
3. **Даты релиза нет.** Сначала полный охват, потом 1.0. podspec и `pod lib lint` появляются уже на этапе 5,
   чтобы владелец мог опубликовать под до закрытия trunk, если захочет. Иначе установка идёт из git по тегу.
4. **Настройки репозитория на GitHub** нужны для выпуска «с документацией», и владелец разрешил довести до него без
   вопросов. Поэтому я включаю Pages с GitHub Actions как источником и создаю Release через `gh`. Секреты не
   нужны: Pages работает на `GITHUB_TOKEN`.

## Stage 15 — differential oracle and scenario simulator

Добавлено 2026-11-13 по просьбе владельца «а мы можем моковый брокер сделать и проверить все все кейсы». Большая
часть API проверена только на кадрах, собранных вручную, а кадры и код написаны по одному чтению ib_async. Мок по
тому же чтению был бы проверкой самого себя. Поэтому сначала независимый оракул для протокола, потом мок, чьи кадры
этот оракул заверяет. План: [`2026-11-13-stage-15-differential.md`](../plans/2026-11-13-stage-15-differential.md).

Решено:

1. **Оракул.** ib_async 2.1.0 запускается локально и в одной задаче CI, только офлайн: без `connect`/`run`, без
   сокетов (подмена `socket.socket` и фабрик соединений asyncio), отправка перехватывается подменой `sendMsg`,
   serverVersion — 178. Генератор и `requirements.txt` с закреплённой версией лежат в `Scripts/differential/`, его
   вывод — закоммиченный JSON в `Tests/IBKRTests/Oracle/`. `swift test` читает только JSON; Python в нём не нужен.
   Задача CI на Linux ставит ib_async, перегенерирует JSON и падает на `git diff --exit-code`.
2. **Разбор.** Все 82 обработчика ib_async при версии 178. Корпус: все кадры, которые уже строят тесты (Fixtures,
   `Recorded/`, кодек-тесты), плюс варианты генератора: пустые и MAX-значения, вложенные счётчики 0/1/n, каждый
   тип тика, каждая ветка сообщения при 178. Сравнение — на уровне декодера: наш `IBMessage` против вызовов
   обёртки, которые делает `Decoder` ib_async, обе стороны в одном каноническом JSON (имя поля ib_async → строка)
   через явное отображение по каждому сообщению. Состояние трекеров выше протокола и проверяется сценариями.
3. **Кодирование.** Все 80 запросов swift-ibkr: полный набор полей ордера (условия, алгоритмы, PEG, комбинации,
   delta neutral, what-if, изменение), рыночные данные, справочники, отмены. Одни и те же входные данные, списки
   полей сравниваются строка в строку.
4. **Расхождения.** Наша ошибка — сначала красный тест, потом исправление. Записанное намеренное различие (строка
   «Disagreements» в `docs/protocol-178.md` или строка `docs/DECISIONS.md`) — запись в списке допусков со ссылкой на
   эту строку; тест проверяет, что ссылка есть и что запись используется. Новое различие без строки — остановка и
   решение контролёра с новой строкой «Disagreements». Никогда не «исправлять» в сторону ib_async вопреки живым
   данным или записанному решению.
5. **Ничего не пропущено.** Тест перечисляет таблицу обработчиков из вывода генератора и падает на любом id без
   кадра в корпусе; допуск для id называет причину.
6. **Мок-брокер.** Слой с состоянием в тестовой цели поверх существующего `FakeGateway` (композиция, не форк):
   ордера, частичные и полные исполнения, комиссии, позиции, P&L, значения счёта; сессия (nextValidId, счета,
   синхронизация); сбои (обрыв посреди потока, коды ошибок, задержки). Сценарии идут через настоящий `IBClient`:
   жизненный цикл ордера, изменение, отмена, отказ, брекет и OCA, what-if, согласие позиций, P&L и исполнений,
